# Begapunk 网站规则索引

状态：当前有效
更新日期：2026-09-05

本目录是 Begapunk 网站规则和上线验收标准的唯一入口。不要在交接记录、操作手册或审计报告中另行制定相互竞争的规则。

## 阅读顺序

1. `BEGAPUNK_WEBSITE_STANDARD.md`：商业目标、内容标准、P0/P1 上线门槛、P2/P3 优化项和授权边界。
2. `BEGAPUNK_RELEASE_AUDIT_STANDARD_V2.md`：把主标准落实为网站、制品、服务器、部署事务、上线后复核和审核器自测规则。
3. `AIDA_WORKFLOW.md`：仅在任务被明确指定为 Aida-GitHub 协作任务时使用。
4. `../../PROJECT_HANDOFF.md`：当前项目恢复入口和稳定技术合同，不定义验收严重级别。
5. `../../DEPLOYMENT.md` 与 `../../i18n/README.md`：操作手册，不是项目决策标准。
6. `../../audit/policy/`：版本化机器控制清单和 release inventory；`audit/` 下其他报告是证据，不是规则。

## 权威来源

不同问题使用不同权威来源，不能互相替代：

- 决定当前允许做什么：用户对当前阶段的最新明确授权。
- 决定产品、业务和合规事实：已确认图纸、正式业务政策和适用于该事实领域的一手资料。
- 决定严重级别、验收和协作边界：BEGAPUNK_WEBSITE_STANDARD.md；决定这些规则如何分阶段取证：BEGAPUNK_RELEASE_AUDIT_STANDARD_V2.md。
- 决定系统实际怎么运行：当前源码、自动检查和经过验证的稳定技术合同。
- 交接快照、操作说明和历史审计报告只提供背景，不能覆盖以上来源。

授权允许执行某项操作，但不会把错误产品事实、安全风险或法律风险变成可接受。

自动检查可以发现问题，但不能自行定义问题是 P0、P1、P2 还是 P3。严重级别必须按照主标准对客户、事实、询盘、搜索和发布安全的实际影响判断。

## 维护规则

- 新的长期决策规则优先修改主标准；复杂执行规则可以放入主标准明确引用的版本化细则或机器控制清单，不新增无权威关系的零散规则文件。
- 日期、页面数量、测试次数、版本号和历史分数都是快照，不得当成永久规则。
- 历史报告中的 P0/P1 标签不会自动继承到当前项目，必须按主标准重新分类。
- 能隔离到单页、单语言或单功能的问题，不扩大为全站阻断。
- 发现矛盾时，先按 P0/P1/P2/P3 分类；只有 P0/P1 才停止当前发布。
