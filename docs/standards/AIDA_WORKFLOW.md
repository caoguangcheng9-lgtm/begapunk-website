# Aida-Codex 人工中继协作运行模型

状态：可选工作流
版本：2.0
适用仓库：caoguangcheng9-lgtm/begapunk-website

## 1. 适用范围

本流程只在用户明确指定“使用 Aida-GitHub 工作流”，或任务来自带有 Aida 入口标签的 GitHub Issue 时生效。

用户在当前对话中直接提出并授权的普通任务，不要求先创建 Issue、等待 Aida 审核或建立 PR。普通任务遵循 BEGAPUNK_WEBSITE_STANDARD.md 的授权和 P0/P1/P2/P3 规则。

本文件不能把 P2/P3 变成阻断项，也不能覆盖用户针对当前阶段的最新明确授权。

## 2. 目标

- Aida 负责提出任务和独立审核。
- Codex 负责在明确范围内实现、验证和报告。
- 老曹负责中继信息，并独立决定是否合并和部署。
- GitHub Issue、PR、CI 和精确 commit SHA 保存该工作流的审计轨迹。

角色标题只是记录标记，不是身份验证。任何角色都不能代替老曹授权合并或部署。

## 3. 任务入口

Aida 自动任务必须同时包含：

- source:aida
- owner:codex
- status:ready-for-codex
- 不含 blocked
- 不含 needs:laocao-decision
- 目标、范围、禁止项和验收标准完整

不满足入口时不实施、不建分支、不猜测缺失决定。

## 4. 单阶段流程

1. Aida 在一个 Issue 中定义目标、范围、禁止项、验收标准和风险。
2. Codex 核对 Issue、Git 状态和已有用户修改，只实施一个已授权阶段。
3. Codex 运行与风险相称的检查，提交 CODEX DELIVERY，列出 commit、文件、验证和剩余风险。
4. Aida 对精确 commit SHA 给出 Result: PASS 或 Result: CHANGES_REQUIRED。
5. 新提交会使旧审核失效；需要重新审核最新 SHA。
6. 老曹决定是否合并。合并后是否部署是另一项独立决定。

发现相邻问题时按主标准分类。P0/P1 可以阻断受影响范围；P2/P3 记录后结束当前阶段。

## 5. 权限边界

| 操作 | Aida | Codex | 老曹 |
| --- | --- | --- | --- |
| 定义 Aida 任务 | 负责 | 检查可执行性 | 决定商业取舍 |
| 修改与本地验证 | 不执行 | 在授权范围内负责 | 接收报告 |
| 独立审核 | 负责 | 回应结论 | 接收完整结论 |
| Git 提交/推送 | 可建议 | 仅在相应授权后执行 | 授权 |
| 合并 | 不授权 | 不自行执行 | 单独授权 |
| 部署和服务器操作 | 可建议 | 获得具体授权后执行 | 单独授权 |

## 6. 合并闸门

只有以下条件全部满足，才能建议合并：

- Aida 对 PR 最新 head SHA 给出 Result: PASS。
- 必需 CI 已通过。
- 没有未解决的 P0/P1 或审核必改项。
- 变更范围与 Issue 一致。
- 老曹明确写出 Action: MERGE PR #<number>。

Result: PASS 只是审核结论，不包含合并授权。

## 7. 部署闸门

部署必须满足：

- 明确被部署的 commit。
- 主标准中的上线前 P0/P1 硬门槛通过。
- 回滚路径可用。
- 老曹明确写出 Action: DEPLOY COMMIT <sha>。
- 部署后完成关键页面和询盘路径检查。

合并授权、推送授权和审核通过都不包含部署授权。

## 8. 停止条件

- 信息不完整或需要商业决定：交还老曹。
- 存在 P0/P1：报告受影响范围和最小下一步。
- 只有 P2/P3：记录后继续完成当前目标，不扩大范围。
- 既定目标完成：立即停止并报告，不继续追求理论完美。
- 真实询盘、对外消息、合并、部署和服务器操作：没有对应授权时停止。

## 9. 紧急情况

只有正在发生的生产 P0 才考虑紧急绕行。老曹必须明确说明故障影响、最小修复范围、回滚方案和事后复核要求。紧急处理不允许顺带实施 P2/P3 优化。
