# Begapunk 网站项目与上线验收标准 v1.0

状态：定稿（v1.0）
生效日期：2026-08-22
适用范围：Begapunk 英文、德文、日文、俄文网站，产品资料、搜索与 AI 可读内容、询盘路径、本地发布包和生产发布

## 1. 网站目的

Begapunk 网站只有三个核心结果：

1. 让目标客户准确理解产品、适用场景和选择条件。
2. 让客户相信技术资料真实、清楚，并愿意提供工况、图纸或询价信息。
3. 让传统搜索引擎和 AI 能正确识别、引用和推荐 Begapunk 的产品与技术能力。

有效询盘是主要商业结果。页面数量、功能数量、技术复杂度、动画效果、Lighthouse 满分和“看起来做了很多工作”都不是项目目标。

### 1.1 获客原则

- **公开信息必须足够有用。** 页面应提供足够的产品事实，让客户和 AI 能判断产品是否值得进入候选名单。不能故意隐藏基本参数来强迫客户询盘。
- **询盘必须带来额外价值。** 客户询盘后应能获得页面无法直接给出的价值，例如选型建议、应用确认、定制接口评估、图纸审核、报价、交期或可提供的技术文件。不得承诺实际无法提供的服务。
- **CTA 必须对应客户当前需求。** 优先使用“获取选型建议”“发送工况或图纸”“申请报价”“确认定制可行性”等具体动作，避免只写空泛的 Contact us。每个获客页面突出一个主要动作，可保留必要的次要动作。
- **以有效询盘衡量获客，不以流量衡量。** 优先吸引真正需要工业旋转接头的客户。网站效果主要看有效询盘数量、产品匹配度、目标国家、应用场景和后续成交机会；访问量、页面数量和关键词数量只是辅助指标。

获客逻辑是：先公开足够信息建立信任，再提供值得询盘的增量价值，降低联系门槛，最后以有效询盘而不是流量判断网站效果。

## 2. 决策与执行原则

- 网站内容与页面决策应从外贸工程师视角出发：既尊重确认的技术事实，也理解海外客户的采购和选型过程。优先回答客户“这是什么、是否适用、为什么可信、下一步需要提供什么信息”，而不是展示内部审核过程、堆砌技术术语或追求页面数量。
- 结论先看客户和商业影响，不因术语、格式或理论完整性无限扩大问题。
- 一次只执行一个已授权阶段；发现相邻问题时先分类，不自动扩展范围。
- 采用最小充分改动：达到既定目标后立即停止、验证并汇报。
- 只有 P0/P1 阻断上线；P2/P3 记录后排期。
- 能隔离到单页、单语言或单功能的问题，只阻断受影响范围。
- 既有且未被本次改动恶化的 P2/P3，不阻断当前任务。
- 自动检查是证据，不是严重级别的裁判。失败结果必须按本标准判断实际影响。
- 不为追求理论完美继续增加页面、功能、规则、测试或技术层级。

## 3. 授权边界

| 操作 | 所需授权 |
| --- | --- |
| 回答问题、分析、草拟方案 | 先回答；默认不修改文件 |
| 修改文件 | 用户明确允许修改，并以当前已说明的文件或阶段为范围 |
| 删除或移动文件 | 用户明确同意具体对象或明确限定的整理范围 |
| Git 提交 | 用户明确要求“提交”；修改授权不包含提交 |
| Git 推送 | 用户明确要求“推送”；提交授权不包含推送 |
| 合并 | 用户明确要求合并具体 PR 或分支 |
| 部署 | 用户明确要求部署具体版本；推送或合并不包含部署 |
| 服务器操作 | 用户明确允许具体服务器和操作范围；部署授权不自动包含无关服务器改动 |
| 真实询盘、邮件或其他对外提交 | 用户单独明确授权 |

任何阶段完成后立即停止并汇报，不继续处理未授权的相邻事项。

## 4. 产品事实与客户文案

### 4.1 事实来源

不同事实使用对应的一手来源：

1. 产品型号、结构、接口、材料、压力、转速、介质和尺寸：优先采用已确认且型号匹配的图纸或正式技术资料。
2. 交期、保修、付款和服务承诺：采用已确认的业务政策。
3. 认证与合规：采用可核对的正式证书或批准记录。
4. 定制或订单专属参数：采用对应订单图纸或书面确认。

网页、翻译、搜索索引、AI 索引和历史审计报告不能反向证明产品事实。来源冲突且会影响客户选型时，停止发布受影响内容并请求一次明确决策。

### 4.2 面向客户的表达

- 已确认事实直接写，不把内部核对过程写给客户。
- QC 编号、图签匹配、内部证据等级，以及 Drawing status、Drawing control、Drawing max、Drawing-listed media、drawing-backed summary 等内部审核语言，不进入主要产品叙述。
- 不能把网站写成免责声明。已确认的参数、能力和适用范围必须明确表达；只有真正未确认且会影响选型的事项，才集中说明一次，并告诉客户需要补充什么信息。不得在页面各处重复使用“可能”“通常”“仅供参考”“需要再次确认”或“请以订单图纸确认为准”等防御性表达。

推荐表达：

| 直接表达 | 不推荐的内部审核式表达 |
| --- | --- |
| 1 MPa · 500 RPM | Drawing max: 1 MPa · 500 RPM |
| Air, oil, water | Drawing-listed media: air, oil, and water |
| 清楚说明适用场景或选择条件 | 展示 Drawing status、QC 编号或图签核对过程 |

不得虚构认证、寿命、性能、客户案例、库存、交期、保修或绝对质量结论。

### 4.3 四语言一致性

- 英文是主要内容母版，明确受控的人工本地化内容除外。
- 德文、日文、俄文必须与英文保持型号、参数、介质、接口、材料、适用范围和限制条件的一致含义。
- 本地语言应符合当地工业采购者的阅读习惯，不要求逐字直译。
- 机器翻译只能作为草稿。记录过的 AI 辅助目标市场逐行审校可以满足发布要求；独立母语或人工编辑审核是可选增强项。
- 不能把 AI 审校描述为母语、人工或专业翻译认证。
- 轻微措辞不自然属于 P2；改变产品事实、适用范围或询盘含义属于 P1。

### 4.4 搜索和 AI 可理解性

核心页面应以可见、可抓取的 HTML 清楚表达：

- 品牌、型号和产品类别；
- 关键参数、适用介质、接口和材料；
- 典型应用、选择输入和真实限制；
- 可验证的技术资料或制造能力；
- 清楚的询盘下一步。

搜索索引、结构化数据、页面正文和 AI 索引中的事实必须一致。不得为了关键词密度、Schema 完整度或“让 AI 推荐”而编造报价、库存、评分、认证、客户或性能信息。

## 5. 严重级别

| 级别 | 定义 | 处理 |
| --- | --- | --- |
| P0 | 已上线的严重故障、安全或隐私事件，正在导致核心网站不可用、敏感信息暴露或询盘严重错投/丢失 | 立即停止相关操作，修复或回滚 |
| P1 | 会让客户得到错误产品事实、无法完成核心操作，或让关键页面无法安全发布的问题 | 阻断受影响范围上线 |
| P2 | 有明确改进价值，但客户仍可正确理解和使用，且不会造成重大事实、询盘或发布风险 | 记录并排期 |
| P3 | 视觉偏好、额外功能、实验性想法或低收益完善 | 有资源时再做 |

### P2/P3 典型情形

- Lighthouse 或 Core Web Vitals 未达到理想目标，但页面仍可正常加载和使用。
- 轻微排版、间距、颜色、动效、图标或非关键可访问性问题。
- 不影响含义的母语润色、文案顺序和术语偏好。
- 非关键链接、可选 Schema、社交分享图、额外 FAQ 或长尾内容不完整。
- 新页面、新功能、框架迁移、更多自动化和像素级统一。

历史报告中的严重级别必须重新按本节分类，不能直接沿用。

## 6. 上线前硬门槛

验收只针对本次发布范围及其会影响的共享区域。以下项目必须通过：

### 6.1 产品与内容

- 本次涉及的型号和关键参数与已确认来源一致。
- 页面没有未经支持的认证、性能、客户、交付或商业承诺。
- 客户能快速看懂产品是什么、适合什么、需要提供什么信息。
- 搜索、结构化数据和 AI 可读内容没有与页面正文冲突的关键事实。

### 6.2 四语言

- 受影响页面的 EN/DE/JA/RU 关键事实一致。
- 没有改变产品含义或询盘动作的翻译错误。
- 文字不会遮挡参数、链接、表格或 CTA。

### 6.3 核心使用路径

- 首页、产品发现、相关产品详情和 Contact/RFQ 路径可达。
- 关键链接、CSS、JavaScript、图片和必要下载不存在阻断性缺失。
- 桌面和移动端能够阅读核心技术内容并完成主要操作。
- 非必要 JavaScript、统计或第三方服务失败时，核心内容和询盘路径仍可使用。

### 6.4 询盘

- 联系方式和主要 CTA 清楚，表单字段与后端合同一致。
- 如果本次修改涉及表单、PHP、SMTP、收件人或服务器邮件配置，必须获得单独授权后完成一次真实送达验证。
- 纯内容或样式发布且询盘链路未变时，不要求重复真实提交；执行本地合同检查和上线后可达性检查即可。

### 6.5 搜索与发布安全

- 受影响关键页面的状态码、canonical、hreflang、sitemap 和 robots 没有严重冲突。
- 发布包可以建立，关键资源完整，不包含密钥、临时文件或本地备份。
- 部署前有明确版本、变更范围和回滚路径。
- 不存在会造成敏感信息暴露、未经授权收集或传输数据、重大误导性合规声明等实际安全、隐私、法律或合规风险。

验收结论只允许：

- READY：所有 P0/P1 已解决；P2/P3 已记录。
- NOT READY：仍存在明确的 P0/P1，并写明受影响范围和下一步。

不得用“还可以继续优化”代替 READY，也不得因 P2/P3 给出 NOT READY。

READY 只表示验收通过，不包含修改、提交、推送、合并、部署或服务器操作授权。

## 7. 与风险相称的检查

| 变更类型 | 最小充分检查 |
| --- | --- |
| 单页文字或参数 | 检查该页事实、相关四语言、主要链接和桌面/移动端显示 |
| 单个产品详情模板或共享样式 | 检查代表性产品页、四语言、桌面/平板/移动端、主要 CTA 和横向溢出 |
| 全站导航、公共 CSS/JS 或生成器 | 检查受影响页面族的代表页、四语言和关键路径 |
| 表单、PHP、SMTP 或收件配置 | 本地合同/语法检查；真实送达测试另行授权 |
| canonical、hreflang、sitemap、robots 或生成流程 | 检查所有受影响路由和生成结果 |
| 纯文档规则调整 | 检查链接、引用、矛盾和 Markdown 差异，不运行部署 |

不要求每次小改动都重跑所有页面、所有分辨率和所有实验室性能测试。共享范围越大，检查范围才相应扩大。

## 8. 自动检查的定位

- 发布前应运行项目当前定义的综合本地检查；具体命令以 package.json 和操作手册为准。
- 自动检查失败时先诊断原因，再按 P0/P1/P2/P3 分类。
- 不得为了得到绿色结果而随意抬高阈值、删除检查或跳过真实风险。
- 如果旧自动化把 P2/P3 当成硬失败，应在单独授权的技术阶段调整自动化；在调整前必须如实报告规则与工具的差异。
- Lighthouse 是性能诊断和回归信号，不单独决定是否上线。

## 9. 上线后持续监控

以下是运营建议，不影响已经完成的上线验收，也不自动成为后续发布的阻断项。

### 每次部署后立即检查

- EN/DE/JA/RU 首页、产品目录、代表性产品页和 Contact/RFQ。
- 关键 CSS、JavaScript、图片、sitemap、robots 和主要重定向。
- 是否出现新的 4xx/5xx、空白页、严重错版或控制台阻断错误。

### 24 小时内

- 服务器错误、404、表单异常和收件情况。
- 搜索抓取是否出现明显异常。
- 新发布页面及相关语言版本是否可访问、可索引。

### 每周

- 核心页面可用性、询盘送达异常、Search Console 主要错误和索引变化。
- 新增 P0/P1 立即处理；P2/P3 进入待办。

### 每月

- 有效询盘数量、来源国家、语言、产品和客户问题。
- 搜索词、核心页面表现、收录覆盖和重要性能趋势。
- 哪些内容真正带来询盘，哪些页面或功能投入回报过低。

上线后监控的目的不是持续追求满分，而是及时发现影响事实、客户使用、询盘和获客的问题。

## 10. 完成条件

一个阶段在以下条件满足时结束：

1. 已授权目标已经实现。
2. 与范围相称的检查已完成。
3. P0/P1 已解决或明确报告为阻塞。
4. P2/P3 已记录但没有扩大本阶段。
5. 已说明修改文件、验证结果和未执行的提交、推送、部署或服务器操作。

达到以上条件后立即停止，不继续追求理论完美。
